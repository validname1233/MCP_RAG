# RAG 基线报告（第一轮）

> 日期：2026-09-27
> 环境：omen6（Ubuntu，Node v24.20.0），KB_DATA_DIR=data-test（独立测试库）
> 语料：157 个真实文件（97 md + 50 pdf + 10 xlsx），scope `kb:group:__ragtest__`
> 标注：84 题（semantic 67 / exact 17 / none 0），覆盖 48 个文档，三轮独立审查背书
> 目的：为 FTS5 混合检索 / rerank / 分块调参等后续优化提供第一组基线数据
> 关联：`2026-09-19-RAG能力测试方案.md`（方案）、`tests/gold.json`（标注）、`tests/gold-review*.md`（三轮审查）

## TL;DR

文档级召回接近满分（**Recall@5 = 98.8%**，MRR 0.964），**块级答案是明确的改进空间**：snippet 命中率 71.4%（多块文档桶 68.1%）——23 条题"正确文档排第一、但含答案的块没进 top-5"。这组差值构成 rerank 立项的直接证据。延迟 P50 220ms，query embedding 主导。全链路（解析→切块→智谱 embedding→LanceDB→检索→评分）在真实语料上端到端首次验证通过。

## 1. 语料与文档分布

157 个测试文件，按格式与入库结果：

| 格式 | 数量 | 解析路径 | 入库成功 | 失败 |
|---|---|---|---|---|
| md | 97 | plain（逐字节原样） | 93 | 3（空文件）+ 1（44 字符纯标题，切不出块） |
| pdf | 50 | MinerU 云端优先 → pdf-parse 兜底 | 49 | 1（金智超汇报，embedding 余额耗尽时倒下，非 gold 未补） |
| xlsx | 10 | SheetJS + tabular 序列化 | 10 | 0 |
| xlsm | 2 | 同 xlsx | 0 | 0（阶段 A 手工分批时未包含，可选补录） |
| **合计** | **157+2** | | **152** | **5** |

**入库库容**：152 searchable 条目，3640 块。

pdf 侧的两个关键事实：
- **16 篇本地 pdf-parse 提取损坏的文件（文字层坏，中文占比 0~24%）全部被 MinerU 成功解析**——云端链路（预签名上传→轮询→zip 下载→unzipSync→content_list→sections）在真实 PDF 上 100% 跑通，此前"手写测试 PDF 解压失败"的疑虑撤销；
- 入库时序上，20 篇试跑（20/20 成功）先行验证链路，再放全量 30 篇（27/30，3 篇倒在智谱余额）——分阶段策略避免了配额白烧。

## 2. 入库性能

分段耗时（阶段 A：md+xlsx 103 篇；阶段 B：pdf 47+2 篇）：

| 段 | 阶段 A（md/xlsx） | 阶段 B（pdf） | 说明 |
|---|---|---|---|
| parse | 479ms 总计（本地解析，近零） | **763s 总计，均值 ~16s/篇** | MinerU 云端往返主导（上传+排队+轮询） |
| chunk | 20ms | 6ms | 纯 CPU，可忽略 |
| embed | 78.9s（211 批调用） | 27.9s + 补录（68+2 批） | 智谱 API 往返，本地解析类文档的主导项 |
| store | 3.0s | 0.7s | SQLite 事务 + LanceDB upsert |
| 吞吐 | 74 篇/分 | 2 篇/分 | pdf 瓶颈完全在 MinerU 排队 |

成本计量：embed 共约 281 批次（16 块/批，~4600 块含 query 侧另计）；MinerU 云端解析 52 次（含 3 次余额失败后的重跑）。期间智谱余额耗尽一次（429 code 1113），充值后补录完成——**quota 监控应进入运维清单**。

## 3. 评测方法

- 指标口径见方案 §0.3；gold 为 query 中心标注（`{query, gold[], type, answer_snippet}`）；
- **文档级 Recall@K**：top-K 内出现任一 gold 文档即命中；
- **snippet 命中**：answer_snippet 出现在 top-K 任一召回块正文（衡量"模型上下文里有没有答案文本"，RAG 真实交付质量）；
- 新增 **单块/多块分桶**（byChunkiness）：单块文档两级指标退化合一（天然高分），多块桶才是有区分度的口径；
- 新增 **snippetMisses 明细**：文档召回但答案块未进 top-K 的题单（rerank 证据）；
- 跑前经 **precheck 84/84 全绿**：gold↔库 searchable 对账 + snippet 对线上真实块文本（MinerU 提取后）严格命中 + 全库唯一性重验，零断行错位、零抢命中——标注的线上有效性确认。

exact 桶 R@5 满分：向量通道在"带文件名精确问"上没有暴露预期弱项——**FTS5 立项的"exact 桶差值"证据本轮为零**，混合检索的优先级应让位于 rerank。

### 4.3 失败明细

**文档级 miss（1 条）**：Q32"简历里这个人在数学竞赛上拿过什么奖"——被 `大数竞赛考场安排表.xlsx` 抢占 top-5。语料引入 xlsx 后出现"数学竞赛"语义强孪生（考场表整表竞赛词汇），单块简历向量被挤出。精确词命中类 miss，是 FTS/关键词通道的典型受益画像。

**snippetMisses（23 条，27.4%）**：全部多块文档，其中 21 条 gold 文档排名 **rank 1**——检索找对了文档，top-5 块里却没有答案块。典型如 Q11（阻燃改性环氧树脂，摘要块未进 top-5）、Q25/Q45/Q46（93 块大论文的摘要锚点块）。完整清单见 `tests/eval-report.json` 的 `snippetMisses` 字段。

执行纪律（踩坑记录，后续复用）：
- **分阶段 = 变量控制**：md 先行是零提取风险的硬地面，四层（切块/embedding/LanceDB/评分）验证通过后，pdf 批次的嫌疑自动收敛到 MinerU 一个变量；
- **SSH 长任务**：输出写远端文件（`> /tmp/xxx.log`）再取，不走管道回传（管道缓冲导致两次"假挂死"判断）；观察进度用短连接直查 SQLite；长连接加 `ServerAliveInterval=30`；
- **非交互 SSH 不加载 nvm**：node 需绝对路径 `$HOME/.nvm/versions/node/v24.20.0/bin`；
- Git Bash 无 rsync，用 scp（109MB 可接受）。

## 6. 结论与下一步

1. **基线成立**：文档级检索质量已高（R@5 98.8%、MRR 0.964），链路稳定，指标可复现（固定 gold + 固定库 + precheck 闸门）。
2. **头号改进项是块级排序**：23 条 snippetMisses 全部"文档对、块不对"，多块桶 snippet 68.1%。→ **rerank 立项**（智谱 rerank API，召回 top-50 → 重排 → top-5，预期 snippet 85%+）。证据链完整：本轮 snippetMisses 清单。
3. **FTS5 降级为观察项**：exact 桶满分，本轮无立项证据；Q32 型精确词 miss（1 条）不足以支撑，待干扰题批次一起重估。
4. **待补齐**：none 干扰题批次（precision 侧盲区）；4 个坏语料文件（3 空 md + Java8.md 纯标题）；2 个 xlsm 与金智超 pdf 可选补录。
5. **运维项**：智谱余额监控（本轮耗尽一次）；MinerU 日配额观察；若做分块参数 A/B，先实现 MinerU 结果缓存（`parseDocument` 前加 `<hash>.json` 缓存层，~20 行）避免重复烧云端配额。
