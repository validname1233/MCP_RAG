# RAG 能力测试方案：入库性能、检索延迟与召回质量

> 日期：2026-09-19
> 状态：方案稿（未实施）
> 目的：独立于生产知识库（群库/个人库），端到端度量 MCP_RAG 的 RAG 能力——入库吞吐、查询延迟、召回率（recall）与准确率（precision），为后续优化（FTS5 混合检索、rerank、分块调参）提供基线数据。
> 关联：`2026-09-17-RAG文档分块调研报告.md`（分块策略依据）、src/ 各模块。

## 0. 总体设计

### 0.1 隔离原则：专用 scope + 专用数据目录，绝不碰生产库

```
生产环境（不动）                      测试环境（新建）
data/kb.sqlite        ←生产库         data/kbtest.sqlite        ←独立 SQLite
data/vectors.lance/   ←生产向量       data/vectors-test.lance/  ←独立 LanceDB
data/files/…          ←生产文件       （测试不需要文件落盘，见 1.2）
scope: kb:group:xxx   ←真实会话       scope: kb:group:__ragtest__（专用隔离键）
```

**为什么独立目录而不是独立 scope 共用库**：测试要高频写入/清空/重建（分块参数实验尤其如此），独立文件可以在测试间直接删除重建，生产库零风险；且 `db.ts` / `vector-store.ts` 的路径目前是模块级常量（`data/kb.sqlite`、`data/vectors.lance`），需要一次小改造让路径可注入（见阶段一技术难点）。

**关于"伪造 key"**：不需要伪造。两条更干净的路——
- **HTTP 层测试**（黑盒）：`.env` 临时加一个 `KB_BEARER_KEY_TEST`？不——我们的服务只有一个主 key。正确做法是**在测试机另起一个进程**（`KB_PORT=3999 KB_MCP_PATH=/mcp` + 独立 data 目录 + 任意测试 key），生产进程完全不动；
- **进程内测试**（白盒）：直接 import `search.ts` / `worker.ts` 的函数调用，绕过 HTTP 和鉴权，最快最稳。

结论：**质量测试（召回率）走进程内白盒**（少一层网络噪声，测的是 RAG 本身）；**延迟测试分两层**——进程内测"纯检索耗时"，HTTP 层测"含网关/MCP 协议的端到端耗时"（用独立端口的测试进程）。你说的"伪造 key"在独立进程方案里自然消解：测试进程的 key 就是真实有效的 key（它自己定的）。

### 0.2 测试数据集：合成文档 + 固定问题集（可复现的关键）

不使用生产文档（不可复现、无标准答案）。合成数据生成器（`scripts/gen-dataset.ts`）产出三样东西：

1. **文档集**（N 份 md，N 可参数化：100 / 500 / 2000）：主题池（如 60 个互不重叠的主题：动物/化学/历史/编程…）× 每主题多篇。每篇 800~3000 字、3~6 个二级标题、若干数据表格段。**每篇埋入唯一的可验证锚点**（如"本篇编号 T-<topic>-<n>，关键事实：<一句独有事实>"）——这是评分的依据；
2. **问题集**（queries.jsonl，每文档 ≥2 问）：
   - 语义型："那种会变色的蜥蜴适合什么温度"（对应爬行类主题文档）
   - 精确型："编号 T-爬行类-3 的关键事实是什么"（测向量通道弱项，将来 FTS 对照用）
   - 干扰型：问题指向数据集中不存在的内容（测 precision/空召回行为）
3. **标准答案**（gold.jsonl）：query → (entry 唯一标识, 关键事实句)。多文档可命中的 query 标注全部合法目标。

随机种子固定（xorshift 或 Node 内置 seeded 方式），整个数据集一键重建、逐字节可复现。

### 0.3 指标定义（先说清口径，免得测完吵）

| 指标 | 定义 | 测量点 |
|---|---|---|
| 入库时间 | 单文档从 parse 开始到 searchable 的墙钟（分项：解析/切块/embedding/落库） | worker 打点 |
| 入库吞吐 | 文档/分钟（串行队列的稳态值；embedding API 延迟是主导项，预期） | 全程计时 ÷ N |
| 查询延迟 P50/P95 | kb_search 单次墙钟；分进程内 vs HTTP 端到端两层 | 检索脚本打点 |
| Recall@K | top-K 结果包含≥1 个 gold 文档的 query 占比（K=1/3/5） | 查询脚本评分 |
| Precision@K | top-K 结果中属于 gold 文档的比例 | 同上 |
| MRR | 首个 gold 结果排名倒数的均值（对"排第一"敏感，rerank 优化的核心指标） | 同上 |

注意：recall 以**文档级**计（chunk 的 entry_id 命中即算），不以 chunk 级计——同一文档多块命中不重复计分，这是 RAG 评测的通行口径（避免切块数量影响分数）。

## 1. 阶段一：基础设施（路径注入 + 数据生成 + 白盒骨架）

**做四件事：**

1. **存储路径可注入**：`db.ts` 与 `vector-store.ts` 的模块级常量改为工厂或环境变量（`KB_DATA_DIR=data-test node …` 即切目录）。方案：两文件改为读 `env.KB_DATA_DIR ?? "data"`，改动各一行，生产行为不变。这是唯一动生产代码的部分，typecheck + 生产冒烟保证无回归；
2. **合成数据生成器** `scripts/gen-dataset.ts`：按 0.2 产出文档集 + queries.jsonl + gold.jsonl，`--n 500 --seed 42 --out testdata/`；
3. **入库脚本** `scripts/ingest.ts`（进程内白盒）：读文档目录 → 直接调 `processEntry` 等价逻辑（或把 entries 插成 queued 后跑 worker 阈）→ **逐文档打点**（解析/切块/embed/落库四段耗时 + 总时）→ 输出 `ingest-report.json`。要点：绕过 web.ts 的 HTTP 层，文件直接从测试目录读；
4. **查询脚本** `scripts/eval.ts`（进程内白盒）：读 queries.jsonl → 逐条调 `kbSearch(scope, query, k)` → 记延迟 → 与 gold 对比评分 → 输出 `eval-report.json`（P50/P95/Recall@K/Precision@K/MRR + 每条 query 的明细，失败 case 单列供人工检视）。

**跑法**（omen6 上）：
```bash
KB_DATA_DIR=data-test node scripts/gen-dataset.ts --n 500 --seed 42
KB_DATA_DIR=data-test node --env-file=.env scripts/ingest.ts
KB_DATA_DIR=data-test node --env-file=.env scripts/eval.ts --k 1,3,5
```

**技术难点：**
- *路径注入的传染性*：`db.ts` 是模块级单例（`export const db`），改路径靠环境变量在**首次 import 前**生效——脚本的 import 顺序要保证（先设 env 再动态 import，参考 qq-bot verify-mcp.ts 的两段式加载模式）；
- *打点插桩的分寸*：不重写 worker，而是给 `processEntry` 加可选的计时回调参数（默认 no-op，生产路径零开销）；
- *embedding 限速*：500 文档 ≈ 数千 chunk ≈ 数百次 API 批调用，智谱按 RPM 限——ingest 脚本内置 429 退避（embed.ts 已有重试，脚本层再加节流间可调）；
- *成本意识*：5000 chunk 一次性约 150 万 token，智谱 embedding 按量计费很便宜但不是零——先 100 文档试跑全链，确认报告形状后再放大。

## 2. 阶段二：基线测量与瓶颈定位

**做三件事：**

1. **跑基线**：100 → 500 → 2000 文档三档，记录各档的入库吞吐、检索延迟分布、质量指标。产出 `docs/2026-09-XX-RAG基线报告.md`（数据表 + 简析）；
2. **延迟分层定位**：eval-report 里把单次检索拆成 query-embedding（API 往返，预期主导）/ LanceDB 搜索 / SQLite 取原文三段——确认"检索慢在哪"，判断 LanceDB 索引（IVF_PQ）何时值得建；
3. **分块参数 A/B**（可选，基线异常时才做）：chunker 的 MIN/MAX/OVERLAP 参数化（同样走环境变量），同数据集跑 2~3 组对照，看 Recall@5 变化——这是调研报告"分块在共识区间内不必调参"论断的实证机会。

**技术难点：**
- *查询向量缓存*：eval 逐条实时 embed 会把 API 延迟算进"检索延迟"且烧钱——query 向量本地缓存（query 哈希 → 向量的 json 文件），重复跑 eval 零 API 成本；分层计时让"纯检索"与"含 embed"两个口径并存，报告里分开列；
- *LanceDB 冷热差异*：首次查询有文件句柄/页缓存预热，正式计时前先跑 20 条 warmup；
- *统计有效性*：每档问题数 ≥200 才有意义（100 文档 × 2+ 问即达标）；干扰型问题占比固定 15%，保证 precision 口径跨档可比。

## 3. 阶段三：端到端（HTTP/MCP 层）与对照实验

**做三件事：**

1. **独立测试进程**：`KB_PORT=3999 KB_DATA_DIR=data-test KB_BEARER_KEY=<测试key> node src/index.ts` 起一个隔离实例（systemd 不动，手动起停或用 systemd-run 临时单元）；bot 不连它，只有测试脚本连；
2. **HTTP 层压测脚本** `scripts/bench-http.ts`：走真实链路（JSON-RPC initialize → tools/call kb_search，Bearer 鉴权）压延迟——口径变为"含协议与鉴权的端到端"，与阶段二的进程内数字对照得出"框架开销"。可顺带测上传 API 的入库触发路径（multipart 直传测试目录）。可选：经 Higress 网关再压一轮（加一层网关延迟的口径，注意别打到生产 28080 端口的进程——**网关层压测要么让管理员配测试路由，要么放弃这层**，独立进程直连已足够回答性能问题）；
3. **对照实验（FTS 前瞻）**：把 queries.jsonl 的"精确型"问题单独评分——预期向量通道在这类问题上 Recall 显著低于语义型。这份差值就是 FTS5 混合检索的预期收益证据，直接指导"要不要做、做到什么程度"的决策。同理可加一组"短查询"（≤4 字）对照。

**技术难点：**
- *协议层脚手架*：不引测试框架，手写 JSON-RPC 客户端即可（约 30 行，我们 e2e 验证时已有 python 版可翻译）；并发压测用 Promise.all 分批（ respects 智谱 RPM）；
- *隔离进程的清理纪律*：测试进程的 data-test 目录用完即删或归档（gitignore 加 `testdata/` 与 `data-test/`），防止下次测试读到陈旧数据；
- *结论的边界声明*：合成数据的召回率 ≠ 真实文档的召回率（合成文本语义更"规整"，向量区分度偏好）——报告必须注明数据为合成，作为**相对基线**（比较优化前后）比**绝对指标**更有意义。这是整个方案最重要的一条 caveat。

## 5. 风险与原则

- **生产零污染**是底线：所有测试走独立 data 目录 + 独立 scope（`kb:group:__ragtest__`）+ 独立端口（HTTP 层）；涉及动生产代码的只有路径注入一处，须 typecheck + 生产冒烟双保险；
- **embedding 费用**可控但需计量：ingest 与 eval 的 API 调用次数写入报告（每次 run 记录 chunk 数 × 批次数），避免不知不觉烧配额（上次余额耗尽的教训）；
- **可复现优先于花哨**：固定 seed、固定参数、报告含环境信息（Node 版本/数据规模/时间），任何人任何时候重跑得到同分布结果；
- **先窄后宽**：100 文档全链路验证脚本正确性 → 再放大规模 → 再上 HTTP 层；不要一上来跑 2000 文档发现评分逻辑有 bug 白烧 API。
