# 召回块的数据结构与 rerank 接入对齐讲解

> 日期：2026-09-28
> 目的：rerank 接入前的数据结构盘点——我们现在召回的"块"长什么样（三段流水线各自的形状）、智谱「文本重排序」API 要求什么、两边的对齐缺口在哪。
> 代码基线：`src/search.ts` / `src/vector-store.ts` / `src/db.ts` / `src/chunker.ts`；API 文档：docs.bigmodel.cn 模型 API-文本重排序。

## 1. 一条块的一生（入库到召回的结构演变）

同一个"块"在链路里有**三种形态**，rerank 接入点决定我们操作的是哪种：

```
chunker 产出 Chunk            SQLite chunks 表（持久层）         LanceDB vectors 表（向量层）
┌──────────────────┐    ┌──────────────────────────┐    ┌──────────────────────────┐
│ index: 7         │    │ id (自增行号)             │    │ vector: float[1024]      │
│ heading: "2 材料" │ →  │ entry_id: 42 (定位键¹)    │ →  │ entry_id: 42 (定位键¹)   │
│ prefix: "xx.pdf·2材料" │ idx: 7          (定位键¹) │    │ idx: 7         (定位键¹)  │
│ text: "正文……"    │    │ heading / prefix / text  │    │ scope: "kb:group:xxx"    │
└──────────────────┘    └──────────────────────────┘    └──────────────────────────┘
```

¹ 复合定位键 `(entry_id, idx)` 是跨存储的锚——向量层只有它+向量，正文全在 SQLite。

**关键点：embedding 的输入是 `prefix + "\n" + text`**（入库时 `embedBatch(chunks.map(c => prefix\ntext))`），但**存储时 prefix 和 text 是分开存的**。这个细节对 rerank 重要（见 §3）。

## 2. 召回后的结构：SearchHit（rerank 要操作的对象）

`kbSearch()` 返回的每条（[search.ts:11-18](../../../src/search.ts)）：

```ts
interface SearchHit {
  entryId: number;   // 文档 id（定位键，来自 LanceDB 行）
  idx: number;       // 块序号（定位键，来自 LanceDB 行）
  filename: string;  // 文档名（JOIN entries 表取得）
  heading: string;   // 小节标题（SQLite chunks 表）
  text: string;      // 块正文（SQLite chunks 表）★ rerank 的输入文本
  score: number;     // L2 距离（越小越相关，方向与 rerank 相反！）
}
```

数据流：LanceDB `.search()` 返回 `[{entry_id, idx, _distance}]`（仅定位键+距离）→ search.ts 拿复合键回 SQLite 批量取 `heading/text/filename` → 按 LanceDB 的顺序拼装。**检索阶段结束了，此时手里有完整的块文本**——rerank 恰好插在"拼装完、返回前"这一步。

规模特征（当前库实测）：9556 块，单块 500~900 字（MIN/MAX），表格行块更短但一块含多行。

## 3. 智谱 rerank API 要求的结构

`POST https://open.bigmodel.cn/api/paas/v4/rerank`，Bearer 认证（与 embeddings 同 key 同平台，`src/embed.ts` 的调用模式可直接复用）。

**请求**：

```json
{
  "model": "rerank",
  "query": "查询文本（≤4096 字符）",
  "documents": ["候选文本1", "候选文本2", ...],
  "top_n": 5
}
```

| 约束 | 值 | 对我们的影响 |
|---|---|---|
| documents 条数上限 | **128** | 我们的候选窗口 K=20~30，远在限内 ✓ |
| 单条候选长度上限 | **4096 字符** | 我们块上限 900 字（MAX），远在限内 ✓ |
| query 长度上限 | 4096 | query 都很短 ✓ |

**响应**：

```json
{
  "results": [
    { "index": 17, "relevance_score": 0.9987 },   // index = 在 documents 数组里的原始下标
    { "index": 3,  "relevance_score": 0.9821 }
  ],
  "usage": { "prompt_tokens": 8532, "total_tokens": 8532 }
}
```

**核心机制：`results[].index` 回指我们传入数组的下标**——API 不返回文本（除非 `return_documents:true`），身份靠 index 保持。所以接入模式是：

```ts
const docs = hits.map(h => h.text);            // SearchHit[] → string[]
const resp = await rerankAPI(query, docs, 5);  // 打分
const reranked = resp.results                  // 按 relevance_score 降序
  .map(r => ({ ...hits[r.index], score: r.relevance_score }));  // index 回填原对象
```

## 4. 对齐缺口清单（接入时要处理的 5 件事）

1. **score 语义反转**：SearchHit.score 现在是 L2 距离（越小越好），rerank 返回 relevance_score（越大越好）。rerank 后的 score 字段要换语义或换名（下游 formatHitsForModel 只用顺序不用 score，风险小，但 eval 报告里会展示——需在报告标注口径）。
2. **送什么文本进 documents**：裸 `text` 还是 `prefix + "\n" + text`？入库 embedding 用的是后者（面包屑参与向量化），rerank 是"第二意见"，**建议同样带 prefix**——让重排器看到的文本与向量是同一篇（`《文件名》· 标题\n正文`），尤其 xlsx 的行块：`表名·sheet | 列: 值` 这种自含形态对 rerank 理解"这行是什么"很关键。待 A/B 验证。
3. **失败降级**：rerank API 挂了/超时不能拖垮检索——catch 后回落向量顺序（rerank 定位为"增强"而非"依赖"）。智谱 429 余额问题已发生过两次，降级路径必须真实可用。
4. **无 key 静默跳过**：同 embedding 的 embeddingEnabled 模式——`RERANK_ENABLED` 未配置时 kbSearch 行为与现在完全一致（eval 的 --channel=vector 基线不破坏）。
5. **延迟叠加**：现在 P50 308ms（embedding 200+ 占大头）；rerank 串行再加一跳 API（预计 200~500ms@20 候选）。eval 的延迟分层口径要能看出这一段。

## 5. 接入后的目标链路（设计预览）

```
kbSearch(scope, query, topK=5)
  ├─ 1. query embedding（不变）
  ├─ 2. LanceDB 召回 top-20/30（窗口由 KB_RERANK_CANDIDATES 控制，KB_MAX_TOPK 放行）
  ├─ 3. SQLite 回表取 text（不变）
  ├─ 4. ★ rerankClient.rerank(query, texts) → relevance_score
  │     ├─ 成功：按分数重排，取前 topK
  │     └─ 失败/未启用：保持向量顺序（现状）
  └─ 5. 返回 SearchHit[]（score = relevance_score，语义切换）
```

eval 侧：`--channel=rerank` 走同一 kbSearch（env 开关），A/B 对照的目标即 K 曲线天花板——窗口 20 → 84.6%、窗口 30 → 87.5%（`tests/docs/评测指标/2026-09-28-召回窗口K曲线.md`）。

## 6. 一句话总结

结构上我们是"幸运"的：**块文本在召回时已完整在手（SearchHit.text）**，rerank 只需 `hits.map(h=>h.text)` 进、`results[].index` 出——没有跨存储取数的额外往返。真正要设计的是语义层：score 方向统一、送不送 prefix、降级路径、开关配置这四件工程小事。
